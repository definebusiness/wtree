# Idea: clone a multi-repository project from its `wtree` configuration

Status: design idea; not an accepted specification or implementation plan.

## Summary

`wtree` already records a hierarchy of independent repositories and their
mounts in `.wtree.yml`. Extending that file with a clone location for every
repository could allow one command to reconstruct the complete checkout tree:

```sh
wtree clone ./acme-shop.wtree.yml ./acme-shop
```

The command would clone the root repository first, then clone each child into
its configured mount. This is deliberately different from Git submodules:
each repository remains independent, with its own normal Git remote, branches,
and worktree administration.

The design must retain the existing distinction between a repository's local
source checkout and its remote clone location. It must also ensure that a root
repository ignores every child mount before any child clone is created.

## Current model

In the current project configuration, `source` is a path to a known local
checkout. `wtree` uses it to discover repositories and administer Git
worktrees. It is not a repository identity and it is not portable to another
machine.

For example:

```yaml
repositories:
  root:
    source: .
    parent: null
    mount: .
    default_branch: main
  backend:
    source: backend
    parent: root
    mount: backend
    default_branch: main
```

This local-path model should remain unchanged. A clone feature needs a new,
portable field rather than redefining `source`.

## Proposed configuration

Each repository could record the remote used to clone it and the exact URL
observed when the project was initialized:

```yaml
version: 1

project:
  id: 3f97ab90-0d41-4bd1-84a8-4df70dbcd221
  name: acme-shop

repositories:
  root:
    source: .
    clone:
      remote: origin
      url: git@github.com:acme/acme-shop.git
    parent: null
    mount: .
    default_branch: main

  backend:
    source: backend
    clone:
      remote: origin
      url: https://github.com/acme/java-backend.git
    parent: root
    mount: backend
    default_branch: main
```

`clone.url` is the intended bootstrap input. `clone.remote` records the remote
name that supplied it, allowing later operations to explain the choice and to
avoid assuming every project uses `origin`.

The feature should not silently derive alternative SSH or HTTPS forms. Those
forms may require different credentials, host aliases, or network access. A
future command may offer an explicit per-repository URL override.

## Capturing clone locations during initialization

`wtree init` can query Git for the selected remote's fetch URL for every
discovered repository and write it into `.wtree.yml`.

Selection needs an explicit policy:

1. Use an explicitly supplied `--remote <name>` or per-repository override,
   when present.
2. Otherwise use `origin` only if it exists and has one fetch URL.
3. Otherwise fail with a diagnostic that lists the available remotes and asks
   the user to select one.

The selected URL is a bootstrap address, not a guarantee of canonical project
identity. The clone operation must still verify the repository hierarchy using
Git after each checkout exists.

## Bootstrap forms

There are two useful invocation forms:

```sh
wtree clone ./acme-shop.wtree.yml ./acme-shop
wtree clone git@github.com:acme/acme-shop.git ./acme-shop
```

The manifest form can obtain its root clone URL directly from the supplied
file. It is suitable for a separately distributed project manifest.

The root-URL form first clones the root, then reads the root checkout's tracked
`.wtree.yml` to obtain the child clone locations. It is the most convenient
form for users, but requires `.wtree.yml` to be committed in the root
repository. An uncommitted configuration generated by `wtree init` cannot
bootstrap a different machine.

`wtree clone <file>` should therefore accept only an explicit file path, not
try to infer whether an arbitrary argument is a URL or a path. A separate
root-URL form can be introduced only when its ownership and configuration-file
requirements are specified.

## Clone transaction

The clone operation should preflight all deterministic conditions before it
changes the destination:

1. Load and validate the manifest, including the repository tree, mounts,
   default branches, and clone URLs.
2. Resolve and validate the destination. It must not exist, or must satisfy a
   narrowly defined empty-directory policy.
3. Verify every child mount is ignored by the root repository's tracked
   `.gitignore` content. Do this from the root commit that will be cloned, not
   from a caller's working tree.
4. Clone the root at its configured default branch.
5. Clone children in parent-first order into their configured mounts.
6. Verify each resulting checkout is an independent repository and that its
   resolved mount matches the manifest.
7. Only after all clones and validations succeed, register the result as the
   default `wtree` workspace.

The root `.gitignore` check is necessary before creating child directories.
Otherwise the root could observe child files as untracked content, and an
interrupted clone would leave a misleading or dirty root checkout. Projects
must commit ignore rules such as:

```gitignore
/backend/
/frontend/
```

The tutorial fixture demonstrates this prerequisite: it writes those rules
before the root repository is initialized.

## Failure and cleanup policy

Network and credential failures are expected during cloning. Diagnostics
should identify the repository ID, clone URL, destination mount, and Git
failure without exposing credentials embedded in URLs.

Before registration, `wtree` owns only directories it created during this
invocation. If a child clone fails, it may safely remove those known-created
directories in reverse order, including the root, but only after confirming
they remain beneath the requested destination. If cleanup fails, report both
the primary failure and the exact remaining paths.

The operation must never delete a pre-existing destination or use a broad
recursive target assembled from an unchecked mount.

## Open questions

1. Should the clone URL be a required field for every repository, or optional
   so projects can keep using local-only configurations?
2. Which Git ref should clone use: each repository's `default_branch`, the
   remote's advertised default branch, or a manifest-pinned commit?
3. Should the manifest support multiple named clone profiles, such as
   `ssh`, `https`, and an internal mirror?
4. Is a separate distributable manifest preferable to committing `.wtree.yml`
   in the root repository, or should both be first-class workflows?
5. Should `wtree init` modify or validate the root `.gitignore` for child
   mounts, or merely report the missing prerequisite?

## Recommended incremental delivery

1. Add optional clone metadata to the configuration model and strict parsing.
2. Teach `wtree init` to capture an explicitly selected repository remote.
3. Add a manifest-only `wtree clone <file> [destination]` with dry-run output,
   exhaustive preflight, and transactional cleanup.
4. Add integration fixtures for SSH-like and HTTPS-like local URLs, missing or
   ambiguous remotes, missing ignore rules, child failures, dirty/pre-existing
   destinations, and registry-publication rollback.
5. Consider the root-URL bootstrap form once committed-manifest semantics and
   URL/profile selection are settled.
